T05/G2 · Dissolve 首帧与场景加载对照

结论：已修补测试的“双方同错却通过”漏洞；画面首帧问题尚未修复，G2 不放行。2026-09-28，Unity 6000.3.18f1 / URP 17.3 / Metal / RenderGraph。unityMCP 本会话未暴露，主 Agent 串行使用 Unity CLI/Pipeline，在主工程交互式 Editor 复验，再用独立的 /tmp 工程副本隔离场景条件。未修改产品 Shader、Frozen Shader、NBPostprocess、官方包、Target、FeatureTier、场景或材质资产；未改变逐像素 0 差和首帧正确的要求，未 push。

先说人话

原测试只问“当前和 Frozen 的第一张图是否一样”。在空场景中，两边第一张图一起错成同一个样子，于是原测试误报通过；第二次绘制时，两边各有 1090 个像素变化。现在测试还问“每一边的第一张图与自己紧接着重画的图是否一样”，所以这种假通过会明确失败。这是补测试，不是预热或修复产品。

可重复的场景对照

先按表格准备场景，再强制重导入当前/Frozen 两个 Shader，确认 Editor ready，运行原 P4 CameraOpaque，随后执行同一 Dissolve mode0 严格夹具。表中“自己变化”是首次图到紧接着重画的不同像素数；正确稳态在固定点 (24,24) 的 Alpha 为 202，异常首次为 255。场景矩阵中的部分行由原测试方法直接调用的临时诊断取得，不冒充正式 NUnit Gate 结果。表头指测试前的场景加载历史；Test Runner 可能临时替换场景，例如两场景正式复验时运行前两个场景已加载，P4 后活动场景已变成临时空场景，不能把表格当成每次绘制瞬间的场景快照。

遮罩内容与材质绑定对照

原遮罩 RGB 为白、Alpha 是纵向渐变；只把 RGB 改黑，主工程失败仍是相同 1090 像素。再把 RGBA 全部改为 0，Frozen 固定点 Alpha 从 202 变为 140，但当前 Shader 异常首图逐字节完全不变；三次当前首图的 原图、RGB 黑、RGBA 零具有同一 SHA-256；临时测试输出为RGB 黑与RGBA 零。异常值与“遮罩采样恒为白”在数值上吻合，但不等于已经证明纹理绑定失败。首帧前对当前材质重设同一个 _DissolveMaskMap，C# 回读仍是同一 Texture 实例，首次失败仍为 1090。临时诊断的RGB 变更、全零变更、重绑定变更未进入正式产品或测试。

本轮正式改动与验证

只在 G2DissolveABTests.cs 的 mode0 首次 A/B 为 0 时增加两侧自重画严格 0 差检查；失败时保存四图和数值。原先首次 A/B 非 0 的诊断及断言保持不变。临时自重画诊断与输入 SHA-256留档。隔离 Editor 编译成功、Console Error 0；空场景中正式测试按预期失败：首 A/B 0、自变化各 1090；两场景加载时正式测试 1/1。主工程同一源码编译后Editor ready、Console Error 0，在原验证场景中原 P4 1/1、Dissolve 仍按原 1090 差失败，不是偷偷让 Gate 通过。主工程受保护的 Quality、原/Frozen 材质及 P4 夹具哈希未变，场景 dirty=false，见哈希与场景状态。

边界与下一步：交互式 Editor 的场景加载历史会影响本用例，隔离 batchmode 副本不能代替它；空场景“两边同错”的 0 差不再视为通过。仍需区分变体首次编译与纹理/状态上传，补实际 ShaderLab Player 首次可见帧，而不是仅用两场景同时加载或多画一帧作为产品修复。MatCap 的跨 Shader 身份 1 像素差是另一个问题；GUI、UIParticle、Compatibility、Player/SVC、性能等 G2 缺口也未因此关闭。验证结束后主工程场景未保存、Editor 按开工前状态关闭。
